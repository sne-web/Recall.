# 📄 Approach Document – Recall.

---

## 🧩 1. Problem Understanding  
Modern meetings generate long, unstructured transcripts that are difficult to navigate. Extracting key decisions, identifying action items, and assigning responsibilities manually is time-consuming and often leads to missed follow-ups and lost information.

---

## ⚙️ 2. Solution Overview  
Recall. is an AI-powered workspace that transforms raw meeting transcripts into structured insights and searchable knowledge. It automatically extracts decisions, action items, and meeting sentiment, and lets users query past meetings through a conversational AI interface that cites its sources.

---

## 🏗️ 3. System Architecture  

```
User uploads .txt / .vtt transcript (React frontend)
        ↓
FastAPI parses it (strips VTT structure, detects speakers) → stored in Supabase Postgres
        ↓
User clicks "Analyse": LLM (Groq, gpt-oss-120b) extracts decisions, action items, sentiment
        ↓
Output validated + normalised → saved as JSON on the meeting row
        ↓
Transcript chunked + embedded locally (HuggingFace all-MiniLM-L6-v2) → ChromaDB
        ↓
RAG chatbot: embed question → top-k chunks across meetings → LLM answers with citations
```

Each stage is a separate service module (`transcript_parser`, `extractor`, `sentiment`, `rag_engine`), and only `llm_client` talks to the LLM provider, so swapping models or providers is a one-file change.

---

## 🤖 4. AI Pipeline  
The AI pipeline uses structured prompting to enforce consistent outputs in JSON format. The model extracts:

- **Action Items** → Who, What, By When  
- **Decisions** → Key outcomes agreed upon  
- **Sentiment** → Overall tone of the meeting  

LLMs don't always follow formatting instructions, so every response goes through a defensive layer: the JSON object is extracted even if wrapped in prose or code fences, a neutral fallback is used if parsing fails, and every field is normalised (e.g. priorities coerced to high/medium/low, `"false"` strings turned into real booleans). The UI and exports can therefore rely on a fixed shape.

---

## 🔍 5. RAG Chatbot  
To enable intelligent querying of past meetings, a Retrieval-Augmented Generation (RAG) system is implemented:

1. User submits a query (scoped to one meeting, or all analysed meetings)  
2. The query is embedded once with the local MiniLM model  
3. The closest chunks are retrieved from each meeting's Chroma collection and ranked globally (top 5)  
4. Those chunks, labelled with their meeting, are passed to the LLM as the only allowed context  
5. The answer is returned with citations built from retrieval metadata (not generated by the LLM), and only meetings whose chunks were genuinely close to the question are cited  

---

## 🗄️ 6. Database Design  
Supabase (PostgreSQL) is used for structured data storage:

- **auth.users** → Managed by Supabase Auth  
- **meetings** → Transcript text, metadata (speakers, word count, status) and the AI output as a JSONB `analysis_results` column  

`meetings.user_id` references `auth.users` with `ON DELETE CASCADE`. The full schema, including RLS policies, is in `supabase/schema.sql`.

---

## 🔐 7. Authentication  
Authentication is handled using Supabase Auth (JWT-based). The frontend stores the access and refresh tokens and transparently refreshes an expired access token, retrying the original request.  
The backend never uses a privileged key for user data. Each request builds a Supabase client that carries the caller's own JWT, so Postgres Row-Level Security policies enforce that users can only read, change or delete their own meetings. The service-role key is used for exactly one thing: deleting an auth user when they delete their account.

---

## 🚀 8. Deployment  

- **Frontend:** Vercel (React UI with CDN delivery)  
- **Backend:** Render (FastAPI + Uvicorn)  
- **Database:** Supabase (PostgreSQL)  

This separation enables independent scaling and better performance.

---

## ⚡ 9. Challenges  

- **Retrieval granularity:** Transcripts are split with LangChain’s RecursiveCharacterTextSplitter (500 chars, 50 overlap) so the chatbot retrieves focused passages instead of whole meetings. Extraction itself sends the full transcript, since the model has a 131k-token context.  
- **Blocking AI calls:** LLM and embedding calls are synchronous, so these endpoints run in FastAPI's threadpool rather than blocking the event loop for other users. The UI shows progress states during the 5–30 s analysis.  
- **Ephemeral vector storage:** Render's disk is wiped on every redeploy, while Postgres persists. Instead of adding another paid service, the vector index self-heals: an empty collection is rebuilt from the transcript in Postgres on first query. Indexing is idempotent, so re-analysing never duplicates chunks, and deleting a meeting or account cleans up both stores.  
- **Messy real-world input:** WebVTT files carry timestamps, cue ids, voice tags and inconsistent line endings (even `
`). A dedicated parser normalises them so neither the LLM nor speaker detection sees timestamps as content.  
- **Model churn:** The original Groq model was retired mid-project. The model is now an environment variable, so the next deprecation is a config change.
